# GPRO Strategy Tool

Made with ❤ by Tushant Sharma

Tampermonkey userscript for gpro.net. Two files: `GPRO_Strategy_Tool.user.js` (logic/UI, ~6800 lines), `gpro-data.js` (season/track/GAPP/calibration/scraped data, ~1580 lines, loaded via `@require`). No build step — verify with `npm run check:userscript` (or `node --check` each file).

## Architecture

1. **Data resolution**: `getDataSmart(endpoint, domParseFn?)` = live DOM parse → long-lived stale cache → real API call. `getDataDomOnly()` never falls through to API. `apiGet()` is last resort (token capped ~100 req/race) — call only via the resolvers.
2. **GAPP-first formulas**: calc functions check `D.gapp` data first, fall back to own calibrated formulas. Key: `calcCarSetupSmart`, `calcTyreStrategySmart`, `calcPartsWear`.
3. **Passive + background capture**: `runPassiveCapture()` on DriverProfile/TrackDetails/Suppliers/StaffAndFacilities/Testing visits; `backgroundCaptureAuxPages()` fetches those + Qualify.asp/NegOverview/TDProfile without navigation, throttled once/30min; `backgroundCacheSeasonTrackSpecs()` pre-fetches all tracks' TrackDetails.asp via Calendar.asp once per season.

## Active Rules

- **After changing `gpro-data.js`: bump BOTH `@version` in the userscript AND the `?v=` on the `@require file://...gpro-data.js` line.** Tampermonkey caches `@require` by exact URL.
- **API is last resort.** Always `getDataSmart`/`getDataDomOnly`, never bare `apiGet()`.
- **DOM parsers** exist for: UpdateCar, QualifyCar, DriverProfile, TrackDetails, TyreSuppliers, StaffFacilities, Testing, AvailList (markets), TdProfile (**never verified against a live TD profile** — flag if its warning fires), Calendar, NegOverview, Weather.
- **Money strings are dot-thousands** (`$5.902.387`) — reuse `parseGproCash`.
- **Escape scraped text before `innerHTML`** (`esc()`) — everything renders via string concat; some values come off gpro.net pages.
- **Every `GM_xmlhttpRequest` sets `timeout: NET_TIMEOUT_MS`.** Without it a hung request blocks the awaiting render path forever (shipped once in `fetchPageHTML`; `ontimeout` does nothing without `timeout`).
- **Fan out via `mapLimit(items, NET_CONCURRENCY, fn)`, not bare `Promise.all`** — past unbounded batches fired 30 and 17 simultaneous page fetches at gpro.net. (Bounded exceptions that exist: ≤5 sponsor negotiations via cached resolver.)
- **Logging via `logDebug()`** (off unless `localStorage.gproDebug==='1'`) / `logError()`. No bare `console.log`.
- **Verdict colors live in shared `VERDICT`; chrome in `PALETTE`/`ST` + `mkSection`/`mkRow`/`mkRec`/`mkInlineBar`/`barStyle`.** Don't re-declare inline; don't hand-roll one-off panel styling. Verdict hues (good/warn/bad/info) are semantic — don't change them casually. `injectGlobalStyles()` is idempotent, called from `createPanel()`.
- **Don't guess numeric constants.** Every calibrated number needs a source (wiki, real result, public repo) stated in a comment.
- **UI stays copy-paste-simple** (explicit repeated user request): backend breakdown sections were deliberately removed from visible panels (see UI trims below); calculations still run internally. Don't re-add clutter without asking.
- **User runs NO practice laps** — goes straight to Q1 on GAPP/derived setups. Never design around a practice-feedback loop.
- **Own heuristics must be labeled as such** in the UI (e.g. "own heuristic — GPRO exposes no formula"), never presented as game formulas.

## Durable bug lessons (each shipped real bugs here — check before repeating)

- **0/falsy ≠ missing for user-derived numbers.** Driver attrs (aggressiveness/motivation/stamina) legitimately sit at 0. Use `numOrDefault(v, def)` (only falls back on genuinely non-numeric), not `parseInt(x) || def` — that pattern existed in 15 places, all fixed. Same class in DOM parsing: use explicit `found` booleans (`wearFound`/`levelFound` in `parseUpdateCarDOM`), never `=== 0`/`> 0` as discovery signals.
- **A valid live DOM reading wins outright over cache** — don't gate merges on value sign/size. Cash bug: `domCash > apiCash` meant post-purchase lower balances could never refresh. Part-wear bug: same gate on `> 0`. Cached cash also refreshes from gpro.asp's Money row every visit.
- **No "largest dollar amount" fallbacks** for financial figures — pages are full of unrelated prices; wrong number < no number.
- **Replace, don't merge, when a snapshot is known-complete.** `mergeMarketRows`'s additive union is only safe for partial views; `ensureFullMarketFetched` replaces `state.rows` with fresh page1+rest and overwrites stale cache, else signed drivers resurface forever.
- **"Field shows a value we never set": check the rendered summary/filterDefaults first** — often a browser form-history or leftover input, not a code regression (`mkFilterBar` only sets `value=` from `defaults`).

## Market advisor (AvailDrivers.asp / AvailTechDirectors.asp)

- GPRO gates its own filters behind Supporter status; we replicate client-side free. **Filter bar is the single source of truth**: `BASE_FILTER_FIELDS`/`DRIVER_ATTR_FILTER_FIELDS`/`TD_ATTR_FILTER_FIELDS` define fields + direction (`dir:'max'`=keep below, `'min'`=keep above) — add new filterable fields there. All fields always editable/fillable. `filterAndRenderMarket` is the ONLY filtering path; `mkFullStatsTable` is a thin ranking wrapper (it once double-enforced hidden floors — real bug).
- **Autofill is direction-aware**: `parseMaxFromTarget` for `dir:'max'` (aggr/stamina `'0-49'`), `parseMinFromTarget` for `dir:'min'`. Charisma/motivation `'0-250'` spans the scale → stays unfilled (no constraint, correct).
- **Pagination/crawl**: `fetchRemainingMarketPages` probes page 2 alone first, then mapLimit batches until empty page (only stop signal), hard cap `MARKET_PAGE_FETCH_MAX=250` (real: 50 rows/page, 92-page markets observed; an earlier cap=15 silently truncated at exactly 750 rows). Live progress callback wired to loading text. Crawl is **deferred until first Apply/Scan** (`ensureFullMarketFetched`, guarded by `state.hasFetchedFullMarket`); pre-crawl view = page 1 + stale cache, labeled partial. `oaMinCutoff` stops early since rows are OA-descending. Read `state.rows` downstream, never the closure `rows`.
- **Scan narrowing**: `cheapFilteredRows` applies Age/Salary/Offers/OA (row-local fields) BEFORE any profile fetch. `MARKET_SCAN_MAX=60` is display-only preview; `MARKET_FULL_SCAN_MAX=12500` is pure runaway backstop (=250×50 ceiling; league OA cap bounds the pool anyway). Scan progress shown live. Deliberately NOT implemented: supporter query-params server-side filtering (unverified response shape could silently under-fetch).
- **autoStart is OFF** (v6.10.1 revert): scan waits for explicit click so user can tighten filters first. Whole-market pagination still auto-runs on load.
- **`recruitmentScore`** (Top Pick card + ranking): weighted attributes by league priority; normalize per-attribute then **invert for `dir:'max'` attributes** (aggr/stamina — high is bad); salary penalty up to −20 scaled by league `maxSalary`; **talent red-flag floor** Rookie `'150+'`/Amateur `'200+'` (matches each entry's own notes; old 60-floor was a leftover artifact); steep talent penalty (up to −45, 0 at threshold) because talent is the one untrainable attribute, **tapered by age** (full ≤22, ~20% by 40+ — heuristic proxy for rebuild-vs-push intent, labeled in code). Reputation scraped/filterable but NOT scored (no sourced weight). Known gaps: `row.retiring`/`row.natCode` referenced in display template but never set by parser — 🕐 icon/nat code silently never render.
- **Filter defaults**: sourced floors autofill inputs (editable, not enforced separately). Salary starts BLANK (user request). Concentration defaults to 200 — **intentional, user-requested, NOT a sourced floor** (concentration has no trustworthy numeric target; see calibration facts). Don't "fix" either back.

## Mixed-condition race weather (`raceProfile`)

`analyzeWeather(weather, totalLaps)` returns a `raceProfile` object that classifies the race as `dry`/`wet`/`mixed` based on per-segment rain probabilities (4 equal segments, threshold ≥40%). The profile handles **multiple transitions** (e.g. Dry→Wet→Dry→Wet):

- **`phases`**: consecutive runs of same condition — `[{condition: 'dry'|'wet', startLap, endLap, laps}]`
- **`transitions`**: lap numbers where condition changes — `[{lap, from, to}]`
- **`tyreStops`**: number of compound changes needed (= transitions count)

This profile drives:
- **Quick Summary**: shows all transitions (e.g. "Lap 14: ☀→🌧, Lap 27: 🌧→☀, Lap 40: ☀→🌧") plus dry/wet fuel split
- **Car Setup** (v6.26.0): the Race column is now optimised for the **DOMINANT** condition (most laps), not the race-start — a fixed setup should serve the majority of the race. E.g. Monza (wet start, 13 wet + 40 dry) shows a **DRY** Race setup but the note says "race starts on rain — use rain tyres for the opening stint". `dominantWet` is computed from `raceProfile.phases` (wetLaps > dryLaps), falling back to `raceWet` when no profile/uniform. `startIsWet` (= `raceWet`, the DOM/segment-1 start) still independently drives the fuel/tyre START compound (rain for Monza) — tyre choice is separate from setup numbers. The mixed-note block shows the alt (non-dominant) setup + transitions, and both the initial render and `updateRaceSetupInPlace` hot-rebuild use `dominantWet` for the Race column.
- **Fuel/tyre**: `calcMixedRaceFuel()` splits total fuel across dry/wet phases using different per-lap consumption rates (wet ~12% higher). Dry compounds in GAPP get weather-transition stops added (minimum stops = transitions count). Legacy fallback also adjusts stop ranges for mixed conditions. `finalizeTyreStrategy` recommends starting dry with transition-lap pit guidance.

`commitRain` still only checks segment 1 (race start) — a race that's dry at start but rainy later gets `commitRain=false`, `raceProfile.type='mixed'`. `isRainAllRace` covers the all-wet case. `raceWet` on the setup page follows the Q2/Race-start DOM widget or segment 1 as before; it now feeds `startIsWet` (the opening compound: rain tyres for a wet start) while the Race setup **column** follows the dominant condition. When the race IS all-wet, both are wet and the setup shows wet values.

## DOM weather widget override

`scrapeSessionTempsFromDOM()` reads `img[name="WeatherQ"]`/`img[name="WeatherR"]` alt text for rain detection. **RaceSetup.asp weather widget overrides forecast-based `commitRain`** via `domRaceWet` parameter passed through `calcTyreStrategySmart` → `calcTyreStrategy`/`calcTyreStrategyGapp` → `finalizeTyreStrategy`. Each function creates its own `analyze = analyzeWeather(weather)` and overrides `analyze.commitRain` with `domRaceWet` when provided. `updateRaceSetupInPlace` re-scrapes DOM on dropdown change.

**Race temperature (v6.26.5)**: Race Setup's Race column temp is GAPP's rTemp — **average of all 8 low/high values across the 4 race-forecast segments** (never the widget's Q2/Race-start box, which is only the race-START reading; a fixed setup serves all 4 segments so a whole-race average is correct). Q1/Q2 column temps DO use the widget boxes (those are single-session readings GPRO shows directly). `scrapeSessionTempsFromDOM()` strategy 1: the widget is COLUMN-BOXES (each session is one cell: icon/condition/Temp/Humidity stacked), so it scans the icon's OWN cell (`img.closest('td')`) first — the old sibling-row scan grabbed the FIRST "Temp:" in the row for BOTH icons (Q2 got Q1's 16°C while owning 14°C — real bug). Fallbacks: `parentElement` textContent, then rank-match of single-value "Temp:" cells vs named icons by horizontal order (kth-leftmost→kth-leftmost), skipping forecast range cells ("Temp: 16°-20°"). The 4-segment forecast table's range cells share the "Temp:" prefix, so filtering those out matters. (v6.26.4 briefly had Race prefer the widget q2 box — reverted same session as user questioned a 14°C race temp; avg of a 16/14/16-20/18-22/17-22/15-18 race is 18.5°C.)

**Stale manual override fix (v6.24.0)**: `resolveSessionWet(gmKey, autoValue)` checks `_manual` flag first — once set by `setSessionWetManual`, it persists forever and blocks DOM auto-detection. Fix: clear `gpro_q1_wet_manual`/`gpro_q2_wet_manual` at start of `renderQualify` and `renderRaceSetup` so each page load auto-detects fresh from the DOM widget. Manual overrides still persist within the same page session (set by dropdown change handlers).

**Wet-start / dry-after mixed profile (v6.25.0)**: `analyzeWeather` classifies the race from forecast segments only. When the DOM widget says rain at race START but the forecast says dry (e.g. Monza: DOM=🌧, segments 5-10%/0%/0%/0%), the tool must start on Rain and pit for dry when rain stops, NOT treat it as dry-whole-race NOR Rain-whole-race. Fix applied in all three `analyze` creators (`renderRaceSetup`, `calcTyreStrategyGapp`, `finalizeTyreStrategy`): when `domRaceWet=true` but `raceProfile.type==='dry'`, **split** the single forecast-dry phase into two phases `wet(1→transLap-1)` + `dry(transLap→end)` (flipping to wet without splitting left the whole race wet — real bug). `transLap≈25% laps`. `finalizeTyreStrategy`'s `commitRain` branch now recommends "Rain at start — pit for dry at lap X". **Fuel/stint anchoring**: tyre transitions are MANDATORY stops; the old `domFuelStart` branch filtered `l > stint1Laps`, wrongly skipping a transition before the fuel-run-out lap (Monza stopped at L24 with Rain through ~10 dry laps). Fixed to build the stop list from transitions+extra fuel stops, sorted; first stop is the wet→dry tyre change at ~L14. **`buildPhaseFuelPlan(laps, phases, transitionLaps, dryRate, wetRate, tyreStops, startFuel)`** (near `calcMixedRaceFuel`) builds a **phase-aware, feasible** per-stint fuel plan for ANY race: each stint = Σ over its laps of the phase-appropriate rate (wet ≈ 1.12× dry) ×1.03; it ALWAYS seeds the compound's tyre-wear stops (spaced across DRY-phase laps only — a trailing wet phase must not stretch the last dry stint — with `wearOnly = tyreStops - transitions` since the strategy's stop count already folds weather transitions in for dry compounds via `max(stops, weatherStops)`), always includes weather transitions, MERGING them (a transition within ~1/3 stint of a wear stop replaces it — that pit already changes tyres), fixed the real bug where ONE Soft set was asked to cover 43 dry laps (the old code suppressed wear stops whenever any transition existed; Q2's fuel rec also lacked `totalLaps` in `analyzeWeather`, so it fell back to a bogus even-split — v6.26.7), and bisects the longest non-first stint until no stint needs more than `TANK_MAX`. New "⛽ Fuel & Tyre Strategy" table (replaced the cluttered Quick-Summary fuel/tyre/weather lines per user request) shows per stint: laps, **tyre** (Rain vs best-dry, resolved by phase), and fuel (start from the plan's **recommended** phase-aware need; after-stop uses `stintFuels`, ≤`TANK_MAX`). Stint-`i` laps = `[bounds[i], bounds[i+1]-1]` with sentinel `laps+1` so the final lap is counted (the old `laps` sentinel dropped lap 53 — off-by-one bug). **Start fuel is the RECOMMENDATION, not the committed Q2 value** (v6.25.x): `stint1Fuel = plan.stintFuels[0]` always — a wet-start race only needs ~72L for 13 wet laps, so echoing a heavy committed value (e.g. 117L from a dry-even-split) as a "recommendation" is wrong. The committed value is kept as `fuel.committedFuel`; the Start cell shows just the rec (e.g. `72L`), and a single amber line appears only when `committed > rec + 25L`: "Start fuel: set ~72L in Q2 (you currently have 117L on the car)". **Deliberately no repeated `(committed X — too heavy)` suffix in the cell and no "⚠️"** — the user found reading the same fact twice annoying (v6.25.3). Checklist item is neutral across all race types ("lighter trims first-lap weight"). Q2's "First Stint Fuel" recommendation (`renderQualify`, initial render + weather-dropdown live update) uses the same `buildPhaseFuelPlan` so it matches Race Setup instead of the dry even-split. **Q2↔Race unified into one system (v6.25.2)**: both pages share `resolveRaceStartProfile(weather, totalLaps, raceStartWet, analyze)` (DNS widget `q2Rain` = race-start ground truth → applies the wet→dry split identically) and `computeRaceFuelPlan(laps, dryRate, profile, tyreStops, committedFuel)` (single source of per-stint stopLaps/stintFuels/startRecommend). Q2 no longer uses the forecast-dry profile NOR the qualify-wet compound for its fuel rec — it recomputes the tyre strategy with `domRaceWet=analyze.commitRain` so `chosen.stops` matches Race Setup's `chosenTyreResult`. Verified all 10 race profiles (dry, wet-start, dry→wet→dry, wet→dry, rain-all, dry→late-wet, dry→wet→dry→wet) produce IDENTICAL Q2 vs Race Setup output. `buildPhaseFuelPlan` coerces every lap bound to an integer (laps are discrete; never fractional).
