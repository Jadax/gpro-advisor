# GPRO Strategy Tool

Made with ❤ by Tushant Sharma

Tampermonkey userscript for gpro.net. Two files: `GPRO_Strategy_Tool.user.js` (logic/UI, ~6800 lines), `gpro-data.js` (season/track/GAPP/calibration/scraped data, ~1580 lines, loaded via `@require`). No build step — verify with `npm run check:userscript` (or `node --check` each file).

## Architecture

1. **Data resolution**: `getDataDomOnly(endpoint, domParseFn?)` = live DOM parse (persisted) → long-lived captured copy (`getStaleData`, marked `__stale`) → null. **No API tier**: the token client (`apiGet`, `getDataSmart`, call budget, token UI, `/Office`) was removed v6.28.2 at the user's request — nothing was being read through it any more. Own driver ID comes from gpro.asp's driver link (`gpro_own_driver_id`), TD from the cached `/TDProfile`, tyre supplier from Suppliers.asp's `activeSupplierName`, league from page group links (else the last captured group). GPRO's OpenAPI spec (`gpro-public-api.yml`, cited in older code comments as a field-name source) was deleted 2026-10-31 to keep the project lean — `git show 3b87890:gpro-public-api.yml` if ever needed. Reference spreadsheets (Heino, MASTER/planner) live outside the repo; their facts are folded into CLAUDE.md/gpro-data.js.
2. **GAPP-first formulas**: calc functions check `D.gapp` data first, fall back to own calibrated formulas. Key: `calcCarSetupSmart`, `calcTyreStrategySmart`, `calcPartsWear`.
3. **Passive + background capture**: `runPassiveCapture()` on DriverProfile/TrackDetails/Suppliers/StaffAndFacilities/Testing visits; `backgroundCaptureAuxPages(homeDoc)` fetches those + UpdateCar.asp (v6.34.1: `parseUpdateCarDOM(root)` + shared `cacheCarFromUpdateCar` — part levels/wear/cash/options refresh without a visit; fetched copies use `docToText`, not innerText) + Qualify.asp/NegOverview/TDProfile without navigation, throttled once/30min and on every autopilot run; `backgroundCacheSeasonTrackSpecs()` pre-fetches all tracks' TrackDetails.asp via Calendar.asp once per season.

## Active Rules

- **Shipping = commit AND push to `origin/main` (github.com/Jadax/gpro-advisor, public).** Since v6.39.0 the user's Tampermonkey copy auto-updates from `raw.githubusercontent.com/Jadax/gpro-advisor/main/` (`@updateURL`/`@downloadURL`) and `gpro-data.js` is `@require`d from there too — an unpushed fix never reaches the game (2026-11-11: a fixed rain-wait bug kept failing because the installed copy was older; the run log now prints the installed version). Always bump `@version` (Tampermonkey only updates on a higher version). Never commit secrets — the repo is public.
- **After changing `gpro-data.js`: bump BOTH `@version` in the userscript AND the `?v=` on the `@require ...gpro-data.js` line.** Tampermonkey caches `@require` by exact URL.
- **No API.** Read data via `getDataDomOnly` / page fetches (`fetchPageHTML`); don't reintroduce a token client.
- **DOM parsers** exist for: UpdateCar, QualifyCar, DriverProfile, TrackDetails, TyreSuppliers, StaffFacilities, Testing, AvailList (markets), TdProfile (**never verified against a live TD profile** — flag if its warning fires), Calendar, NegOverview, Weather, RaceAnalysis (**text-based** on `body.innerText`, built from screenshots, never checked against live markup — its "couldn't read" warning means send a screenshot).
- **Money strings are dot-thousands** (`$5.902.387`) — reuse `parseGproCash`.
- **Escape scraped text before `innerHTML`** (`esc()`) — everything renders via string concat; some values come off gpro.net pages.
- **Every `GM_xmlhttpRequest` sets `timeout: NET_TIMEOUT_MS`.** Without it a hung request blocks the awaiting render path forever (shipped once in `fetchPageHTML`; `ontimeout` does nothing without `timeout`).
- **Fan out via `mapLimit(items, NET_CONCURRENCY, fn)`, not bare `Promise.all`** — past unbounded batches fired 30 and 17 simultaneous page fetches at gpro.net. (Bounded exceptions that exist: ≤5 sponsor negotiations via cached resolver.)
- **Logging via `logDebug()`** (off unless `localStorage.gproDebug==='1'`) / `logError()`. No bare `console.log`.
- **Verdict colors live in shared `VERDICT`; chrome in `PALETTE`/`ST` + `mkSection`/`mkRow`/`mkRec`/`mkInlineBar`/`barStyle`.** Don't re-declare inline; don't hand-roll one-off panel styling. Verdict hues (good/warn/bad/info) are semantic — don't change them casually. `injectGlobalStyles()` is idempotent, called from `createPanel()`.
- **Don't guess numeric constants.** Every calibrated number needs a source (wiki, real result, public repo) stated in a comment.
- **UI stays copy-paste-simple** (explicit repeated user request): backend breakdown sections were deliberately removed from visible panels (see UI trims below); calculations still run internally. Don't re-add clutter without asking.
- **User runs NO practice laps** — goes straight to Q1 on GAPP/derived setups. Never design around a practice-feedback loop.
- **Own heuristics must be labeled as such** in the UI (e.g. "own heuristic — GPRO exposes no formula"), never presented as game formulas.

## Durable bug lessons (each shipped real bugs here — check before repeating)

- **`node --check` passes ≠ runs.** Runtime scope errors (e.g. referencing a caller-local variable inside a shared helper — `finalizeTyreStrategy` used a `track` variable that only existed in its call sites, shipped v6.27.1) survive syntax check AND ship. When extracting/hoisting math into a harness, call the extracted functions, don't just parse them.
- **0/falsy ≠ missing for user-derived numbers.** Driver attrs (aggressiveness/motivation/stamina) legitimately sit at 0. Use `numOrDefault(v, def)` (only falls back on genuinely non-numeric), not `parseInt(x) || def` — that pattern existed in 15 places, all fixed. Same class in DOM parsing: use explicit `found` booleans (`wearFound`/`levelFound` in `parseUpdateCarDOM`), never `=== 0`/`> 0` as discovery signals.
- **A valid live DOM reading wins outright over cache** — don't gate merges on value sign/size. Cash bug: `domCash > apiCash` meant post-purchase lower balances could never refresh. Part-wear bug: same gate on `> 0`. Cached cash also refreshes from gpro.asp's Money row every visit.
- **No "largest dollar amount" fallbacks** for financial figures — pages are full of unrelated prices; wrong number < no number.
- **Check units when a data-file value feeds a formula.** `D.wearPerLap.base` held WHOLE-RACE wear (Chassis 21, Engine 37) but analyzeCar/the multi-race projection multiplied it by laps as PER-LAP → the Car Advisor's "End (own)" column read 100% on every part. Removed (v6.27.6); one shared own model `ownPartRaceWear` (PART_BASE_RACE_WEAR × driverFactor + CTR term) now serves calcPartsWear, analyzeCar and the projection.
- **Replace, don't merge, when a snapshot is known-complete.** `mergeMarketRows`'s additive union is only safe for partial views; `ensureFullMarketFetched` replaces `state.rows` with fresh page1+rest and overwrites stale cache, else signed drivers resurface forever.
- **A `//` comment appended to a data line kills every key after it on that line** (v6.28.1 near-miss: a "digit fixed" note on the `fuelFactorCoeffs` line commented out `aggressiveness` → fuel NaN; `node --check` passed, the tyre harness caught it). Put comments on their own line in multi-key object literals.
- **"Field shows a value we never set": check the rendered summary/filterDefaults first** — often a browser form-history or leftover input, not a code regression (`mkFilterBar` only sets `value=` from `defaults`).

## Mixed-condition race weather (`raceProfile`)

`analyzeWeather(weather, totalLaps, lapsPerPeriod)` returns a `raceProfile` object that classifies the race as `dry`/`wet`/`mixed` based on the four forecast windows (threshold ≥40% on each window's max rain%). Windows map to ABSOLUTE laps per track via `estimateLapsPerWeatherPeriod(track)` (passed by call sites; flat Losail fallback 20) because the forecast windows are 30-minute periods tied to Elite pace (wiki), NOT quarters of the race — the old `totalLaps/4` split put Portimao's rain transition at L18 instead of L21 (fixed v6.27.1, was previously defined-but-never-called dead code). Window 4 extends to the final lap; windows the race never reaches are dropped (short races must not inherit their rain). The profile handles **multiple transitions** (e.g. Dry→Wet→Dry→Wet):

- **`phases`**: consecutive runs of same condition — `[{condition: 'dry'|'wet', startLap, endLap, laps}]`
- **`transitions`**: lap numbers where condition changes — `[{lap, from, to}]`
- **`tyreStops`**: number of compound changes needed (= transitions count)

This profile drives:
- **Quick Summary**: shows all transitions (e.g. "Lap 14: ☀→🌧, Lap 27: 🌧→☀, Lap 40: ☀→🌧") plus dry/wet fuel split
- **Race Setup Weather tile** (v6.27.1): uniform races show DRY/RAIN, 2-phase mixed shows DRY→RAIN/RAIN→DRY (warn tone), 3+ phases show MIXED — the old plain DRY read as a contradiction next to a plan that pitted for Rain mid-race (Portimao report)
- **Car Setup** (v6.26.0): the Race column is now optimised for the **DOMINANT** condition (most laps), not the race-start — a fixed setup should serve the majority of the race. E.g. Monza (wet start, 13 wet + 40 dry) shows a **DRY** Race setup but the note says "race starts on rain — use rain tyres for the opening stint". `dominantWet` is computed from `raceProfile.phases` (wetLaps > dryLaps), falling back to `raceWet` when no profile/uniform. `startIsWet` (= `raceWet`, the DOM/segment-1 start) still independently drives the fuel/tyre START compound (rain for Monza) — tyre choice is separate from setup numbers. The mixed-note block shows the alt (non-dominant) setup + transitions, and both the initial render and `updateRaceSetupInPlace` hot-rebuild use `dominantWet` for the Race column.
- **Fuel/tyre**: `calcMixedRaceFuel()` splits total fuel across dry/wet phases using different per-lap consumption rates (wet ~12% higher). Dry compounds in GAPP get weather-transition stops added (minimum stops = transitions count). Legacy fallback also adjusts stop ranges for mixed conditions. `finalizeTyreStrategy` recommends starting dry with transition-lap pit guidance.
- **Fuel/boost/contingency realignments (v6.27.3, S113 R1 Portimao result)**: ~~start stint safety margin 1.06, later stints 1.03~~ (superseded v6.27.7 — see "Pit-lap convention" below). `calcBoostLapSuggestion` takes an optional `stopLapsHint` — when the fuel plan is known, boost sets anchor 2 laps before each REAL planned pit instead of the old even-split guess, and the Fuel & Tyre table tags `⚡n` boost laps per stint with per-boost-lap fuel folded into the shown fills (capped at TANK_MAX). The F&T bar total is the **carried sum of fills incl. boost** — the old bar printed `tyre.totalFuel` (dry-only mixed estimate) and contradicted the fills in the same box (S113 screenshot). Wet-contingency line: when any wet-phase forecast window averages ≤55% rain, the strategy tells the user to fit the best dry compound instead at a forward pit if the sky dries (S113: forecast said rain to the flag, race actually dried from L43).
- **v6.27.4 (S113 R2 Bremgarten result — plan followed to the liter, won from pole, fastest lap)**: (a) the **LAST stint gets a 1.06 margin** (now `LAST_STINT_SAFETY`; the first/middle-stint margins were replaced in v6.27.7) — the final fill at +3% ran to within 2L of dry and, unlike a mid-race stint, there is no pit behind it to recover a dry-out; (b) **boost fuel is now estimated on every track with a known lap length** — tracks missing from TRACK_PROFILES (Bremgarten) previously fell to "can't estimate", so fills silently carried no boost fuel; fallback is `FUEL_BASE['Medium']` with an "assumed Medium" note (`FUEL_BASE[trackFuelRating] || FUEL_BASE['Medium']`), and the no-data note only fires when the lap length itself is unavailable; (c) the **Start F&T row and the Q2 "First Stint Fuel" rec now carry stint 1's physical boost share** (⚡tag on Start; Q2 note says "Includes ~XL for the ⚡N boost lap(s) in stint 1") — the old even split (total boost ÷ all stints) drifted the Q2 rec from the Race plan; (d) boost picks are anchored to the plan's stop laps on Q2 too (q2Plan computed before the boost pick, `stopLapsHint` passed) so both pages pick the same boost laps. ## DOM weather widget override

`scrapeSessionTempsFromDOM()` reads `img[name="WeatherQ"]`/`img[name="WeatherR"]` alt text for rain detection. **RaceSetup.asp weather widget overrides forecast-based `commitRain`** via `domRaceWet` parameter passed through `calcTyreStrategySmart` → `calcTyreStrategy`/`calcTyreStrategyGapp` → `finalizeTyreStrategy`. Each function creates its own `analyze = analyzeWeather(weather)` and overrides `analyze.commitRain` with `domRaceWet` when provided. `updateRaceSetupInPlace` re-scrapes DOM on dropdown change.

**Race temperature (v6.26.5)**: Race Setup's Race column temp is GAPP's rTemp — **average of all 8 low/high values across the 4 race-forecast segments** (never the widget's Q2/Race-start box, which is only the race-START reading; a fixed setup serves all 4 segments so a whole-race average is correct). Q1/Q2 column temps DO use the widget boxes (those are single-session readings GPRO shows directly). `scrapeSessionTempsFromDOM()` strategy 1: the widget is COLUMN-BOXES (each session is one cell: icon/condition/Temp/Humidity stacked), so it scans the icon's OWN cell (`img.closest('td')`) first — the old sibling-row scan grabbed the FIRST "Temp:" in the row for BOTH icons (Q2 got Q1's 16°C while owning 14°C — real bug). Fallbacks: `parentElement` textContent, then rank-match of single-value "Temp:" cells vs named icons by horizontal order (kth-leftmost→kth-leftmost), skipping forecast range cells ("Temp: 16°-20°"). The 4-segment forecast table's range cells share the "Temp:" prefix, so filtering those out matters. (v6.26.4 briefly had Race prefer the widget q2 box — reverted same session as user questioned a 14°C race temp; avg of a 16/14/16-20/18-22/17-22/15-18 race is 18.5°C.)

**Stale manual override fix (v6.24.0)**: `resolveSessionWet(gmKey, autoValue)` checks `_manual` flag first — once set by `setSessionWetManual`, it persists forever and blocks DOM auto-detection. Fix: clear `gpro_q1_wet_manual`/`gpro_q2_wet_manual` at start of `renderQualify` and `renderRaceSetup` so each page load auto-detects fresh from the DOM widget. Manual overrides still persist within the same page session (set by dropdown change handlers).

**Wet-start / dry-after mixed profile (v6.25.0)**: `analyzeWeather` classifies the race from forecast segments only. When the DOM widget says rain at race START but the forecast says dry (e.g. Monza: DOM=🌧, segments 5-10%/0%/0%/0%), the tool must start on Rain and pit for dry when rain stops, NOT treat it as dry-whole-race NOR Rain-whole-race. Fix applied in all three `analyze` creators (`renderRaceSetup`, `calcTyreStrategyGapp`, `finalizeTyreStrategy`): when `domRaceWet=true` but `raceProfile.type==='dry'`, **split** the single forecast-dry phase into two phases `wet(1→transLap-1)` + `dry(transLap→end)` (flipping to wet without splitting left the whole race wet — real bug). `transLap≈25% laps`. `finalizeTyreStrategy`'s `commitRain` branch now recommends "Rain at start — pit for dry at lap X". **Fuel/stint anchoring**: tyre transitions are MANDATORY stops; the old `domFuelStart` branch filtered `l > stint1Laps`, wrongly skipping a transition before the fuel-run-out lap (Monza stopped at L24 with Rain through ~10 dry laps).
